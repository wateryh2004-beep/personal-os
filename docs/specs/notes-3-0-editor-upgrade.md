## 1. 产品目标与明确非目标

目标：保留现有 CodeMirror 6 与 Markdown 权威正文，将 Notes 提升为快速、轻盈、视觉有层次、可以安全进行全文 AI 润色和整合的个人知识写作空间。

使用者强调：现有编辑器总体令人满意；本轮不可推倒重做。按优先级解决 3–4 秒的新建与切换延迟，随后增加飞书式整段色块、简洁的文字颜色和背景高亮，接入 OpenAI 模型，升级全文 AI 编辑与对照，最后精修页面视觉。

非目标：不改为 ProseMirror/Tiptap/JSON 文档权威；不创建第二套笔记数据库；不在未经确认时自动覆盖正文；不全面重做 Today/Career/Calendar；不以撤销认证、版本、RLS、审计、草稿恢复或私有缓存边界换取速度；不把原有 DeepSeek 能力一次性移除。

## 3. 指标定义与阶段门槛

必须区分五个时间点：点击反馈、导航开始、编辑器可输入、首份可靠正文展示、后端持久化确认。统计 p50/p95，至少针对 20 次正常网络测试及单独的冷/暖样本，记录设备、网络、环境、部署、样本量、区域、文档大小。不要把 localhost、CI 合成延迟、部署 READY 当成生产性能结论。

目标（正式基线测量后可登记调整原因，不能为了通过测试偷偷放宽）：

| 指标 | 目标 |
| --- | --- |
| 点击→视觉 pending/焦点反馈 | 100ms 以内 |
| 已访问笔记→有用缓存内容 | p95 不超过 200ms（沿用主性能规范） |
| 新建→可输入空白编辑器 | p95 不超过 800ms；未确认持久化前不得假称已保存 |
| 未缓存笔记→可用工作区框架 | 正常网络约 1s，目标 p95 不超过 1.5s |
| 100KB 以内典型长文输入 | 输入无明显停顿；明确记录 INP、Long Task 和帧丢失 |
| 数据可靠性 | 无已确认内容丢失、重复创建、串档、越权、AI 静默覆盖 |

错误与慢网络需要清楚展示待确认/失败状态。对于极慢网络，不以不可达的服务端返回时间指标掩盖实际问题。

## 4. P0 性能专项（先执行，性能达标后再扩富文本）

### P0.1 可观测性与即时交互（当前首批范围）

- 为 Notes 列表与单篇文档读取加入与其他 workspace 一致的后端延迟标记，分离 auth 与读取耗时；只记录阶段、时长、请求状态和随机 trace ID，不记录笔记 ID、标题、正文、token 或身份资料。
- 给主要新建入口提供立即的 pending 视觉反馈和重复提交保护，保留 Server Action 的鉴权和成功跳转。
- 维持既有原子事实边界：这一步不迁移数据库、不修改正文格式、不移动审计与版本持久化。
- 对创建 Server Action 的认证、文件夹校验、主表写入、初始版本和审计分阶段计时；是否进入持续日志以现有 PERF_DEBUG 约束为准。
- 交付：代码差异、请求耗时记录说明、回归范围。没有线上鉴权真实测量时如实说明。

### P0.2 新建笔记快路径

- 依据 P0.1 时延证据判定瓶颈：身份校验、跨区域往返、主表/初始版本/审计串行、revalidate、RSC、加载 CodeMirror。
- 首选在数据库事务/RPC 内完成必要的初始写入与版本/审计，保证失败时不出现半成品笔记。涉及 SQL/RLS/事务时单独 migration、权限和回退验收；严禁未经验证直改生产库。
- 前端可显示独立的临时空白写作表面；它必须保留所有输入，成功后绑定真实 ID，失败后允许重试/恢复，不得将临时内容错误并入另一篇笔记。
- 列表只进行必要的 owner-scoped 缓存协调，避免全工作区刷新；不得把未提交成功显示为已保存。
- 交付：创建失败、弱网、双击、重试、刷新与离开页面的完整用例和实测前后数据。

### P0.3 左栏切换快路径

- 将 route 读取、数据请求、编辑器挂载、重绘分别计时。
- 复用现有文档缓存和最近 6 篇的内存预算；在受控 hover/focus 或明确交互意图时限量预加载，跳过 Save-Data、过慢网络与未授权状态。
- 已缓存内容优先展示，后台比对修订；不牺牲未保存草稿与冲突弹窗；切换时保留光标、选区、滚动和 Undo。
- 避免旧请求覆盖新文档与多余 router.refresh()；不引入共享 CDN 私有缓存。
- 交付：100 次交替切换与返回、离线/失效、权限改变、文档删除与分页索引回归。

### P0.4 长文编辑专项

- 以 5KB/50KB/200KB 文本、50/200 段、表格、图片、重复标题等合成场景测输入、粘贴、撤销、目录更新与滚动。
- 优先修无谓 React re-render、全量 Markdown 解析、重复布局测量和主线程重任务；保留增量 CodeMirror rope 和 IME。
- P0 收口：数据正确性检查全通过、真实性能样本达标或明确记录剩余瓶颈及归属。

## 5. P1 色块、颜色与 Markdown 兼容

### P1.1 语义与设计规范

已落实的色彩 Token、交互与对比度规范见 [P1.1 专项规格](notes-3-0-color-system.md)。当前 P1.1 不包含正文语法、颜色菜单及旧笔记改写；编辑/阅读/导出的一致性由 P1.2 实施。

推荐 5 个低饱和度、适配暖白与深灰绿的背景色：雾蓝（信息）、杏橙（提醒）、柔红（重要）、鼠尾草绿（思考）、暖灰（引用）。语义为推荐用法，不强制用户按类别使用。正文色彩与背景高亮互相独立；所有色值建共享 token，不散落硬编码。

明确卡片形态、左缘强调线、内边距、文本对比度、focus/hover/readonly 状态、暗色/强制色兼容，以及嵌套 Markdown、长文本与小屏行为。

### P1.2 规范化存储与解析

整段色块优先采用兼容的 GFM admonition/引用形式（如 > [!NOTE]），先验证现有 CodeMirror/remark 与所有导出链路的兼容性，再冻结最终规范。文字颜色/行内高亮没有标准 Markdown 格式：先对比严格受限的内联扩展与可迁移降级方案，明确语法、转义、纯文本回退、编辑器解析、跨平台导出及安全处理，经过测试后采纳唯一实现，不把任意 HTML style 原样信任或开启无约束的 rehype-raw。

### P1.3 操作路径

- 文本选区浮动工具栏：文字颜色、高亮、清除格式、转整段色块。
- 斜杠菜单：信息、提醒、重点、思考、引用色块；支持键盘和中文输入法。
- 全局顶部工具栏：仅显示简短颜色入口，不加一排大按钮。
- 色块可以修改类型、撤销/重做、在源码模式中编辑、跨段粘贴、复制 Markdown、恢复版本。
- 阅读/编辑、导出 HTML/PDF 与全文搜索保持一致。对旧笔记完全向后兼容。

### P1 验收

编辑/阅读视觉一致，Markdown 可用且可迁移；语义内容在降级阅读中不丢失；无任意 HTML 注入风险；正文与文字的色彩对比度达标；桌面/手机、长文与撤销测试通过。

## 6. P2 AI 写作 3.0

### P2.1 提供商层

- 将目前 DeepSeek 专用的类型/选择器改为 Provider-neutral 的服务端 adapter、模型能力注册表、按任务路由与有限的模型白名单。
- 新增 OpenAI API Provider（通过 Vercel AI SDK 合适的官方包），保留 DeepSeek 兼容运行；服务端保管密钥、显式预算与失败回退，不把模型密钥放浏览器。
- 界面上使用“快速编辑 / 高质量写作 / 深度审查”三种用途，不强迫用户理解具体模型代号；进阶设置才展示实际模型。
- 先核实 OpenAI API 组织能否访问目标模型、组织速率限制及额度是否真实激活。ChatGPT 订阅与 API 分开计费；每月约 100 美元仅适用于符合官方条件、已激活的 Pro 100 类权益，不能默认认定已有额度。
- 对比真实质量、中文一致性、首 token 延迟、费用和失败率，再决定默认路由；不先写死“某模型一定更好”。

### P2.2 AI 编辑工作区

- 保留现有“全文润色/整理结构/选区润色/翻译/提问”等能力，重做入口、结果组织与结构化 diff，而不是复制建设一套平行助手。
- 允许全文、章节、当前选区三个作用域；给出“轻润色 / 结构整合 / 保留原声 / 精简 / 逻辑审查”明确定义。
- 长文分块生成、锚定段落、汇总一致性、进度可见、失败可重试，不丢失任何原始事实、专有名词、数字和内部链接。
- 逐段接受/拒绝/重新生成，整篇覆盖需要明确确认，并在原修订号不变时提交 CAS。修改前创建可靠恢复快照，不把 diff 颜色混进正文语义。
- AI 来源保存到版本/审计元数据，不强制在每篇笔记正文最前面插入“由 AI 生成”分割线。注意现有数据库字段的兼容迁移。
- AI 不默认主动跨笔记抓取上下文；仅 normal 且符合当前明确开关/作用域的内容可进入模型，sensitive/never 始终服务端隔离。
- 对 AI 请求执行长度/预算限制、结构保真测试、完整性比对与个人表达风格约束。错误明确区分额度不足、网络、权限、模型不可用与版本冲突。

### P2.3 质量基准

固定 15–30 份合成笔记（口述碎片、专业研读、日记、表格链接、长文、矛盾文本），由用户现有偏好定义事实保真、可读性、结构一致性、语气保真、过度改写、输出成本等评测指标。模型升级必须对比旧版基线，不能仅凭主观“更聪明”通过。

## 7. P3 视觉系统与内容组织精修

以 Notes 为首批：标题与工具区、目录树、文档纸面、选区浮层、AI 工作区、状态反馈、阅读/编辑过渡、窄屏工具布局、夜间配色、键盘和减少动态效果。优先减少重复标签与非必要按钮，保证暖白背景、深灰绿主强调、低饱和度色块和统一字号/间距。增加可选写作专注模式，不另造新的 Markdown 引擎。

视觉验收以 390px 手机、1440px 桌面为基本矩阵，并覆盖 360px、768px、短屏、200% 字号、长文/表格/空态/失败状态。基于真实但脱敏或合成内容做截图/交互检查；不因获得构建成功就宣布美学验收完成。

## 8. 阶段执行规程、交付物与发布

每阶段固定闭环：读取最新 main 与现行规范 → 对照上一阶段的变更/未解决问题 → 先形成子范围的目标与验收 → 独立分支实现 → 类型/单测/相关集成与端到端测试 → PR 记录性能/视觉证据 → 审查风险、合并 main → 核验部署 → 记录实际成果与遗留问题。

不强制一轮完成全部 4 个阶段；不得因阶段文档已写好就谎称功能已上线。阶段之间必须回读最新 main，避免不同会话覆盖对方已提交修改。大改拆为 P0.1/P0.2/P0.3/P0.4、P1.1/P1.2/P1.3、P2.1/P2.2/P2.3、P3.1/P3.2，各阶段以真实验证作为完成条件。

通用硬门槛：不丢原始 Markdown、不破坏标题/草稿/版本/附件/正文内链/表格、严格 owner/RLS、无密钥泄漏、不伪造保存成功、不覆盖用户编辑、不引入大面积 UI 卡顿；有新迁移时必须明示部署顺序和回滚/兼容策略。测试需要覆盖创建失败、并发保存、离线、文档切换、读写冲突、IME、撤销、前后端 Markdown 格式一致、AI 拒绝写入与取消。

版本与交付记录格式：阶段编号、main SHA、PR、涉及文件、行为前后对比、实测条件、p50/p95、跑过的检查、未跑的检查与原因、生产是否部署、回退点。相关检查包括 npm run typecheck、npm test、npm run lint、npm run build、编辑器 E2E、权限/RLS 与导出测试；按变更风险执行，不机械地夸大。
