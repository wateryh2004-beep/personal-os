# 环境、发布、运行与恢复手册

状态：有效规范与操作手册。维护日期：2026-10-14。适用范围：Personal OS 的 GitHub、Vercel、Supabase、R2、Microsoft 与模型服务。具体操作仍受任务授权与实际资源权限约束。

## 资源与环境登记

| 环境 | 用途与边界 |
| --- | --- |
| 本地 / 合成 CI | 假数据、localhost 接口、短期数据库；不注入生产秘密或真实私人原件 |
| 独立验证资源 | 验证真实 SDK、权限和存储协议；操作前核对项目和精确测试对象 |
| Preview | 验证候选代码；优先隔离后端，缺隔离时关闭真实写入；问题答案恢复按当前实现始终关闭 |
| Production | 正式业务数据；资源身份、变更范围与已有授权均核对后操作 |

仓库为 `wateryh2004-beep/personal-os`，正式域名之一为 `https://personal-os-kappa-nine.vercel.app`。域名只是访问入口；操作前通过对应连接核对当前项目、环境、部署提交和数据库目标，不凭名称相似选择资源。

运行登记应包含服务、用途、环境、所有者、区域、稳定入口、配置名称、备份与手册位置。可在私有仓库记录非秘密资源标识；不记录密码、密钥、真实恢复答案、访问令牌或带签名的 URL。

当前尚未由本文建立统一自动监控、自动备份调度或成本告警；这些是否生效必须以配置与真实运行记录验证。

## 配置与秘密

变量名及用途以 `.env.example`、`src/lib/env.ts` 与对应适配层为依据。生产秘密通过服务商的 secrets/env 管理；查验优先读取名称、目标环境与状态，不取回明文。

更改配置记录变量名、环境、用途、是否需重新部署和验证步骤，不记录值。轮换前检查依赖、加密数据兼容性与失效窗口；更新后验证新配置并按计划撤销旧值。不能把用于解密历史连接的密钥当作普通可随意替换的字符串。

新增付费资源、扩大调用预算或订阅需已有相应授权；普通任务不自动升级套餐。配置缺失时明确相关功能不可用，保留不依赖该配置的功能。

## 发布前

1. 确认目标任务、PR、head SHA、base、工作树及用户已有授权；检查是否存在并发变更。
2. 按 [质量规范](quality-standards.md) 核对实际检查和相关产物，说明未验证项。
3. 列出代码、数据库、环境变量、外部权限和计划任务的变化；文档变更不等于运行配置已改变。
4. 有数据库或状态格式变化时，确定旧/新代码兼容窗口、回填、备份和恢复方法。
5. 核对预览/生产资源身份与功能开关，不向浏览器或日志暴露配置。

## 发布顺序

一般采用兼容的 schema 扩展 → 代码部署 → 有限启用 → 运行验证；每个有特殊依赖的变更在自己的规格中写清顺序。权限收紧、凭据轮换、缓存格式和后台任务变化不能机械照搬顺序。

通过 PR 合并，记录实际 merge commit。已获准合并/上线时完成相应工作，不再次索取同一授权；创建文档的任务只建立文档，不自动执行数据库迁移、配置轮换或生产数据写入。

Vercel 构建成功、部署 READY、域名指向正确、用户流程可用分别检查。确认正式域名对应的提交与配置；不能只根据预览地址声称已上线。

## 发布后检查

| 检查 | 范围 |
| --- | --- |
| 可用性 | 相关页面/API 正确响应，未认证访问被正确处理 |
| 功能 | 使用授权范围内的只读或精确测试流程；不重置真实密码来验收 |
| 数据与权限 | 迁移版本、RLS/ACL、对象访问和必要数据校验 |
| 界面与动效 | 对应视口及完整流程，确认性能与减少动态效果 |
| 运行 | 检查明确时间窗口的错误、任务、连接与同步状态 |

没有错误日志不等于完整功能已通过。发布报告记录提交、环境、实际检查时间、结果和恢复入口。

## 观察与排障

关注认证拒绝、API 错误率/延迟、供应商失败、同步陈旧与冲突、上传/解析/导出作业、AI 预算和存储容量。按用户影响设置可行动的阈值与通知，先确认通知对象和渠道授权。

日志只记录必要的错误码、请求关联 ID、领域、耗时和聚合量，不保存正文、token、签名 URL、完整 provider 响应或模型提示词。诊断开关限受控环境，不引入生产控制台循环。

故障时先确认影响范围、开始时间、最近部署/配置/供应商变化；查 [系统状态](system-status.md)、[日历运行手册](calendar-sync-operations.md)、文件领域契约及相关日志。先保护数据，再恢复功能；避免广泛重试导致重复外部写入。

## 回退与事故

| 影响 | 处理原则 |
| --- | --- |
| 权限泄漏、数据损坏或秘密暴露 | 优先限制相关写入/访问并保留证据；在已授权范围内处置、轮换或修复 |
| 核心流程不可用 | 核对兼容部署/配置，采用回退或前向修复 |
| 局部视觉或次要功能异常 | 有界修复，保留主要工作流与已输入内容 |

回退前核对新 schema、对象状态、客户端缓存与旧版本兼容性。代码回退不代表数据库或外部操作已撤销；不要逆向删除新数据。必要时先关闭相关功能，保留可读资料。

事故记录使用 [模板](templates/incident-record.md)，保存脱敏时间线、影响、根因、恢复证据和后续预防；避免将推测写成已确认原因。

## 备份与恢复

遵循 [系统备份与隔离恢复](system-backup.md)。数据库、R2/历史 Storage 原件、代码与必要配置分别覆盖；明确备份时间与一致性，不把 Git 当数据库备份。

目标可接受数据损失窗口和恢复时间需要结合当前能力测量、登记；本文不捏造 RPO/RTO 承诺或已配置的每日备份。新增自动调度、目的地或上传按对应任务授权处理。

恢复先在隔离目标验证格式、计数、校验和、关系、原件和排除项，再在已授权范围内执行实际恢复。备份可下载不代表可以恢复。不要自动删除不确定的原件、版本、队列或测试对象。

## 成本、保留与交接

登记 Vercel/Supabase/R2、AI、后台任务与带宽的主要消耗和预算；配置请求/并发/重试/输出上限。供应商价格和配额随时核对实际账号与官方资料，避免写死未经验证的长期承诺。

日志、备份、产物和任务保留按用途明确；没有确定策略时不擅自设置永久清除。CI 合成证据的保留期以工作流配置为准。

交接材料只含项目控制方式、资源关系、配置名、运行检查与恢复方法，秘密通过受控渠道转移。交接后验证权限和恢复能力，并在授权范围内撤销不再需要的访问。
