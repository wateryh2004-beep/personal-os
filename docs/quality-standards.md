# 质量、验收与性能规范

状态：有效规范。维护日期：2026-10-14。适用范围：代码、数据、文档、界面和发布验证。

## 完成的定义

目标行为已实现，相关数据与安全不变量成立；适当检查实际执行，结果与限制被记录；必要文档和回退说明已更新。能构建不等于能完成用户流程，测试通过不等于已验证真实生产。

规范要求与当前自动化覆盖分开。CI 的实际步骤以 `.github/workflows/` 为准，不能因为本文要求某项检查就声称已配置阻断规则、真实设备测量或生产监控。

## 按变更风险选择验证

| 变更 | 应验证的内容 |
| --- | --- |
| 文档、注释、低影响文案 | 链接、路径、事实、规则冲突、差异格式；无需机械运行整套浏览器或为措辞写测试 |
| 业务逻辑 | 真实行为的正常、边界、失败和相关回归；类型与受影响 lint |
| 表单、交互、导航 | 真实事件、状态与焦点、输入保留、取消、返回历史、重复操作、失败恢复 |
| 视觉、动效 | 代表性视口、长文/空态/失败态、截图；完整操作录屏、连续点击、反向与中断 |
| 身份、权限、凭据 | 匿名、有效 owner、非 owner、过期状态、伪造输入、客户端/日志泄漏和正确拒绝 |
| 数据库、同步、批处理 | 干净安装与升级、RLS/ACL、跨用户引用、唯一性、事务、并发、重试与恢复 |
| 文件与导出 | 原件/元数据一致、完整性校验、大小分页、pending/cancelled、权限和可恢复范围 |
| 依赖或构建链 | 安装/构建产物、受影响运行路径、二进制/资源、许可与安全边界 |

测试针对可观察行为和不变量，不能只复述实现。可逆低影响样式调整以视觉检查为主，不为每个像素创建脆弱测试。涉及失败恢复、权限、并发和数据完整性的测试应保留。

## 当前仓库检查入口

```bash
npm ci --ignore-scripts
npm run typecheck
npm test
npm run lint
node scripts/system-standards-audit.mjs --check
npm run build
node scripts/check-runtime-closure.mjs
npm run audit:ui
git diff --check
```

上面是入口清单，不是每个小修改都要执行的固定套餐。安装和构建前核对当前 `package.json`、lockfile 与构建前资源生成要求。`audit:ui` 当前为提示性审计，不冒充阻断式检查。

`System standards v2` 工作流执行全仓 lint、明确规则的源代码门禁、构建与部署闭包检查，再用合成 Chromium 场景验证 390/1440px、原生页面过渡、弹层开闭/焦点/中断与减少动态效果，保存截图和独立连续录屏。`check-runtime-closure.mjs` 必须在构建后运行；它核对已知 CLI 告警链是否进入实际加载和部署清单，不是全部依赖的安全证明。静态规则、人工追踪项和实际覆盖见 [全系统排查](verification/2026-10-14-system-standards-v2.md)，剩余告警见 [依赖复核](security/runtime-dependencies-2026-10-14.md)。

标准 Verify 工作流包含类型、Vitest、构建、合成浏览器和若干 SQL 场景；另有 Document continuity、Private OCR、Question recovery、System backup recovery 等工作流。名称和覆盖以当前工作流文件为准；其中 Document continuity 指文件阅读/恢复连续性，不是 Markdown 文档链接检查。

本轮新增 `Project documentation`：`node scripts/check-project-docs.mjs` 检查仓库内 Markdown 链接、可识别锚点、必要入口和 34 主题编号，不安装应用依赖，不访问外部网站或生产服务。局部文档快照可显式传入 `--inventory` 与固定提交的完整路径清单，结果必须标记为快照检查；CI 在完整 checkout 中不使用该选项。该检查不能证明内容事实、视觉与运行正确。

全仓 lint 若有存量问题，固定基线比较文件/规则/位置并单独报告本次新增问题。受影响文件检查成功不能写成全仓 lint 成功。新失败必须定位，不通过删除断言或降低检查掩盖。

## 界面与可访问性矩阵

至少检查受影响的 390px 手机和 1440px 桌面；布局变化再覆盖 360px、768px、短屏与 200% 文字放大。使用键盘、触摸、可见焦点、屏幕阅读语义和减少动态效果验证关键任务。

标准正文目标对比至少 4.5:1，大字与必要控件边界目标至少 3:1；按实际渲染和状态测量。阴影不作为唯一控件边界。手机主要点击区域至少 44px，输入文字至少 16px。

动画检查完整轨迹及最终状态，不只看某一帧。快速点击、Esc、返回、切页、后台标签和网络失败后仍应可操作。减少动态效果和强制颜色设置独立检查。

## 性能与容量

沿用 [性能规范](performance.md) 与 [资源所有权契约](performance/navigation-resource-ownership.md)：点击产生的局部反馈目标小于 100ms；已访问工作区的有效缓存展示目标不超过 200ms。它们是待测预算，不能当作已达到的线上事实。

动效总时长遵循 [动效规范](design/motion.md)，与操作反馈延迟分别测量。登录可有约 1 秒的空间过渡，按钮按下与开始验证仍应立即反馈。

每组性能证据记录：提交/部署、设备/浏览器、视口、地区/网络、数据量、冷/暖状态、采样次数、指标定义与结果；样本足够时报告中位数与 p95，不用一次最快样本代表整体。新预算先建立可重复基线。

明确区分点击反馈、路由提交、可用内容、数据就绪、外部写入确认。合成延迟与本地计时不代表真实 Supabase、用户网络或中国大陆体验。容量变化测量分页、索引、内存、上传/导出大小与背景请求数量。

## 证据与外部验证

优先使用合成数据、独立数据库、受控临时对象和独立验证服务。真实生产写入只在现有授权范围内执行；不为测试修改真实 owner 密码、不自动清理未知对象。

截图、录屏、运行日志与报告不得包含秘密、恢复答案、私人正文或未授权个人数据。证据记录环境、命令、退出码、产物及观察，不保存完整认证 payload。

验证记录使用 [验收模板](templates/verification-record.md)。未运行写“未运行及原因”；没有线上证据写“未验证”；已运行但失败写明失败与影响，不能以“脚本已准备”替代结果。

## 合并与发布

本次新增缺陷、破坏安全/数据不变量或关键流程失败时先修复。无关存量问题明确登记，不强迫把每次小修改扩大为全仓重构。合并和部署的实际状态分别报告；发布顺序与恢复见 [运行手册](release-operations.md)。
